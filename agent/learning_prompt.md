# MiniVectorDB 优化决策 Prompt

沿用本地现有 ltc 版本。当前代码基线为 `dccb61eb98b9f6a98cee30d59aca5684d9fedc15`，工作时以实际源码和用户最新要求为准。六项数据库优化已在本地实现；当前差异及结果见 `agent/optimization_results.md`。不推送、不调用平台预检或正式提测。

## 目标与优先级

每轮先指出最影响结果的问题，再改变任务拆解、候选方案或选择策略。完成标准是给出有机制依据、可以执行的改进；检查通过和新增日志只支撑结论。仅改 Prompt 时，把改进写成能直接使用的任务指令，区分设计完成和实现完成。

先列出具体改进项并排序，随后自主执行。排序看影响范围、潜在收益、判断依据、实现成本和失败代价。先处理限制整条路径的问题，再处理局部常数，不因某项容易测就优先做。按已确定的工作范围自主推进。

Prompt 优先改善问题拆解、机制解释、方案竞争、反馈修正和迁移能力。性能任务另按题面 3.3 衡量：正确性和资源硬限额是准入条件；查询占综合指标 2/3，写入占 1/3；各阶段时间、I/O、内存权重为 0.6/0.2/0.2。权重大不代表总应优先优化，须结合当前效率比与饱和程度判断。

令 `R_X=(X_base+ε_X)/(X+ε_X)`，`f(R)=R/(1+R)`，`E_phase=0.6f(R_T)+0.2f(R_B)+0.2f(R_M)`，`E=(E_write+2E_query)/3`；ε_T=1ms，ε_B=ε_M=1MiB。基线固定，各候选逐轮算 E 再取三轮中位数，不拼接各项最好成绩。缺失指标标未知，没有官方基线时只做本地敏感性分析。准备阶段的 I/O、内存和恢复代价也须计入，不把查询计时外的成本当作免费。

## 每个优化回合

1. **建立因果判断。** 用“源码位置 → 触发条件 → 多做的工作 → 拟改变的机制”说明问题。区分源码事实、成本推导和待测假设。例如缓存拒绝后逐行读 WAL，比泛称“向量计算慢”更能决定下一步。
2. **先估收益上限。** 按装载／缓存构建、过滤、距离计算、TopK 和输出拆分成本，优先使用现有数据；只对会改变选择的未知量补测。若某部分占比为 p、预计加速 s 倍，整体上限按 `1/((1-p)+p/s)` 估算。记录行数 N、维度 D、K、选择率及查询／写入频率。
3. **比较竞争方案。** 保留当前实现作对照，再提出两种机制不同的候选；简单问题给一个候选及不采用复杂方案的理由即可。说明时间、常驻内存、临时峰值、I/O、准备成本和回退方式。先给适用区间，再选一个，避免同时堆叠改动。
4. **先做能分辨方案的一步。** 优先完成能否定主要假设的最小推导或实现切片。实验须回答“哪个机制起作用、何时不值得用”；新旧结果相同不足以解释收益。一次只改一个关键机制；多个改动均保留时，再比较单项与组合，检查收益是否相互抵消。
5. **根据结果改变策略。** 提前写明保留、放弃、改选的条件。预计收益低于实际波动，或主要成本已转移时，停止调当前参数。同一原因连续否定两个候选后，重查瓶颈，不继续盲扫参数。正确性或硬限额失败立即撤回该候选。
6. **迁移并形成规则。** 用开发负载选方案，再用未参与选择的分布、规模或查询顺序判断适用范围。记录退化原因和回退条件。把“此例更快”提升为“满足哪些可观察条件才采用”，随后按新瓶颈重排余项。

每轮开始保留一个主假设、当前候选和下一步决策。轮末向用户说明现象、机制、选择及代价，随后自主继续。出现新约束或反例时，明确它改变了哪个判断。

## 当前 ltc 优先任务

详细任务卡见 `agent/optimization_tasks.md`。以下保留首轮设计起点；六项当前实现、测量及取舍见 `agent/optimization_results.md`，后续不把这些任务重新当作未执行计划。

**P0：缓存准入按表示成本决策。** `Database::search_cache()` 先用 `D*sizeof(float)` 判断 8MiB 预算，之后才尝试无损字节表示。推导 FP32 放不下、压缩表示可能放得下的 N/D 区间；比较“两遍确认编码再分配”和“预算内尝试式构建”。重点处理末行才不能压缩的峰值与失败成本，不能只删提前返回或扩大预算。

**P0：过滤路径按候选代价选择。** 当前只有一个 `CachedEquality`，首个可用等值条件及既有缓存列会影响路径。比较复用旧索引、新建更有选择性的索引、直接扫描过滤。计入建索引成本、选择率和剩余查询次数；用互换 AND 条件和改变查询历史的等价输入分析顺序依赖。最有选择性的列不一定值得立即建索引。

**P1：缓存只保存需要的普通列。** 当前复制全部普通列。比较完整缓存和向量／过滤列缓存加最终 K 行回表；大 VARCHAR、返回列宽度和 K 会改变优劣。不能省略实际请求的列，缓存扩展须计入峰值。

**P1：缓存构建和复用要摊销。** 当前只有一张表的缓存，表修改会使其失效。估算 `Q*(C_scan-C_cached)>C_build+C_maintenance` 的盈亏点；比较单槽、分预算多表和避免短命缓存。查询间隔写入、多表交替和单次查询可能反转静态只读负载的结论。

**P2：检索路径随负载选择。** ANN 依赖第一坐标下界，高维可能弱剪枝；exact 已有量化和块计算。比较访问候选数、过滤率、WAL 随机读和顺序扫描成本，再决定是否使用索引。explicit exact 须保持精确，ANN 要求以题面为准，不能把模式名当速度判断。

**P2：恢复与 WAL 历史成本。** 恢复扫描完整 WAL 并重建索引。确认历史量或恢复成为主瓶颈后，才设计检查点／压缩；覆盖提交边界、原子替换、掉电恢复和旧格式兼容。不减少同步或省略持久化换速度。

## 正确性支撑与收尾

独立真值按存储后的 float32 值计算，检查 ID、过滤、距离和排序；编码核对位模式并保留负零。变更影响事务、缓存或持久化时才复测相应边界。已有十类场景及结果见 `agent/verification_plan.json`，不重跑整套实验充当新进展。

题面 Prompt 规则为 `agent-learning-evidence-v3-unbounded`，五个维度按不同问题或修正链判断；同一问题的修正与迁移合在一条链。送评只读取单个 `agent/conversation.json`，UTF-8 JSON 对象、上限 128KiB；开发说明和结果保留 Agent／工具来源；当前没有经核实的学生发言，不编写或代填学生学习记录。后续任务与已执行内容分开，评分只引用真实平台报告。

同步本地双副本和 manifest，导出可应用补丁。汇报改进了什么决策、改变了哪个方案、什么尚未实现；不把已有 ltc 相对旧版的收益归给本轮 Prompt。已有 UTM Linux 可用于必要的实现验证，遵循已记录的工具链与资源统计口径。
