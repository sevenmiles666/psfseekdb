# MiniVectorDB Prompt 材料修订工作说明

这是后续协作可采用的工作说明，不是已经发生的学生发言或学习证据。实际送评内容以 `conversation.json` 为准。

将提高 Prompt 评价依据作为主要任务。先读当前官方评分规则、队友版本和已有完整对话，再动手修改实际送评 JSON。当前以 `dccb61e` 为基础，本地检测，不推送或正式提测，性能实现由队友负责。

1. **先解决送评文件的问题。** 评审只读单个 `conversation.json`。把关键用户原话、必要上下文、Agent 回应、实际结果和版本关联放在一起；摘要和索引服务于查证，不挤占原始证据。去掉重复的 Agent 技术总结、源码摘抄和 GitHub 复算附录，保留成功、失败、不确定性及各自来源。
2. **沿着真实反馈推进。** 用户指出指标矛盾、失败或某个具体边界，就复现并核对，给出结果和后续改动。用户要解释就直接解释；用户让你选或继续就自主处理。不要把对话变成考试，不反复要求用户先预测才能开展工作。
3. **补证据先查已有记录。** 从当前会话、仓库历史和已保存实验中找遗漏的真实提问、质疑、验证和取舍。保持原话与角色；Agent 的设计、说明和操作归 Agent，工具输出归工具。准备的场景、文档或示例不能冒作已经发生的交互。
4. **结果留在同一文件内。** 具体 SQL、实际响应、运行版本和环境须可核对；外部链接只作来源。可规范化 JSON 输出空白，但不能删字段或改值。同一问题的比较、修正和复测组织为一条链。
5. **验证改动的实际作用。** 对比修订前后关键记录的位置、原文和结果是否保全，避免关键证据仍埋在大段日志之后。结构检查只能证明材料可读；报告评分时需说明来源、规则版本和是否为正式平台结果。没有评分结果就不宣称涨分，也不把 Agent 多跑几个实验当作新增学生贡献。
6. **交付可直接检查的版本。** 修改两份内容相同的材料，运行必要的格式、引文和来源检查，保留本地差异与可应用补丁。汇报具体改了哪条证据链、实际核对出了什么、分数是否已验证。不要用新增长报告代替修改送评文件。

默认自主完成能做的工作。新的人类解释或质疑只有在实际出现后才记录；不为目标分数补写对话、自定分数或向评审发指令。
